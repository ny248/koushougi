# 広将棋ソフトウェア開発計画

広将棋のルールを検証できるゲームエンジンを先に作り、そのエンジンを対局画面と自己対戦による強化学習で共用する。開発は「ルール仕様の確定 → エンジン → 対局画面 → 探索AI → 学習基盤 → 棋力評価」の順に進める。

最初の到達点は、人が広将棋を最後まで遊べること。次の到達点は、手元のGPU搭載PCで自己対戦、学習、評価、再開を繰り返せること。その後、固定した対戦相手との比較で棋力向上を確かめる。

## 1. 開発対象と完成条件

| 成果物 | 開発対象 | 完成条件 |
| --- | --- | --- |
| ゲームエンジン | 盤面、駒、合法手、状態遷移、特殊効果、成り、終局、棋譜 | 採用したルールの全項目に検証例があり、棋譜から同じ局面と結果を再現できる |
| 対局アプリ | ローカルでの人対人・人対AI、操作支援、保存と再開 | 通常の移動と特殊な行動を画面から選択し、対局を完了・再生できる |
| AI訓練基盤 | 探索、自己対戦、学習データ、モデル更新、評価、途中再開 | 手元のGPU搭載PCで一連の処理を実行し、モデルと実験条件を保存できる |
| 棋力の評価 | 固定AI・過去モデルとの対戦、局面問題 | 同じ計算条件で改善の有無を判定し、勝敗数と不確実性を報告できる |

初期版はローカル利用を対象とする。オンライン対戦、アカウント、クラウド運用、複数GPUによる分散学習、スマートフォン専用アプリは初期開発の範囲に含めない。

訓練環境はユーザー所有のGPU搭載PCとする。GPUの機種・メモリ容量、OS、CPU、メモリ、保存領域は未確認であり、モデル規模と訓練時間は実機測定後に決める。

## 2. 最初に確定する広将棋のルール

初期版のルールは、A-kasakaの「広将棋のルール紹介(網羅版)」を基準とする。記事は『廣象棋譜』に基づき、曖昧な箇所には著者の解釈を加えている。本文と図から、初期配置、駒の動き、特殊効果、成り、終局条件を実装用の仕様に落とし込む。[広将棋のルール紹介(網羅版)](https://akasaka0x16.blog.fc2.com/blog-entry-116.html)

最初の工程で、次の項目を仕様とテスト用局面に落とし込む。

| 確定する対象 | 仕様に記載する内容 |
| --- | --- |
| 盤と初期配置 | 座標、先後の向き、駒の識別子、初期配置、枚数 |
| 通常の移動 | 方向、距離、飛び越え、遮蔽物、移動と捕獲の違い |
| 複数段階の行動 | 経路、途中の捕獲、途中での終了、元の位置への復帰 |
| 射撃と特殊効果 | 対象の選択、射程、遮蔽物、捕獲できない相手、効果の優先順 |
| 成りと駒の状態 | 成る条件、連動する変化、変化の発生時点、履歴への依存 |
| 終局 | 勝利対象となる駒の組合せ、合法手がない場合、反復、投了 |
| 記録 | 一手の境界、行動の表記、保存すべき状態、ルールの版 |

ルールごとに「出典の該当位置」「採用する解釈」「入力局面」「期待する合法手・結果」を対応づける。同じルールで行われた公開対局の棋譜を使い、記事の読み取りと実装後の合法手・局面の変化を検証する。記事と棋譜を照合しても判断できない箇所だけをユーザーに確認する。採用したルールには `ruleset_version` を付け、異なる版の棋譜・学習データを混在させない。[広将棋の対局記録](https://akasaka0x16.blog.fc2.com/blog-entry-163.html)

## 3. システム構成

ゲームエンジンは、画面・探索・学習から独立したライブラリにする。対局画面やAIが独自に合法手を判定せず、共通のエンジンを呼び出す。

```text
対局画面 ── ローカルAPI ── ゲームエンジン
                  │               ↑
                  └── 探索AI ─────┘
                          ↑
                    学習済みモデル
                          ↑
自己対戦 → 学習データ → 学習 → 候補モデル → 評価 → 対局用モデル
    └──── ゲームエンジンと探索AIを使用 ────┘
```

技術構成は、仕様変更のしやすさを優先して次を推奨する。

| 部分 | 技術候補 | 選定理由 |
| --- | --- | --- |
| エンジンの初期実装 | Python | ルールの確認と局面テストを小さく反復し、学習コードと接続しやすくする |
| AIの探索と訓練 | Python、PyTorch | 局面の評価値をNNで学習し、αβ探索で着手を選ぶ |
| 対局画面 | TypeScript、React、SVG | 盤面・座標・経路・射撃対象を表示し、拡大表示に対応する |
| 画面との接続 | PythonのローカルAPI | 画面と訓練で同じエンジンを使用する |
| 初期の保存 | JSON形式の棋譜、分割した学習データ、モデル保存ファイル | 単一PCで管理し、外部サービスへの依存を抑える |
| 計算負荷の高い処理 | 測定後にRust等への移行を判断 | 合法手生成や探索が律速の場合だけ高速化する |

Pythonだけでは自己対戦速度が不足する可能性がある。初期実装を正しさの基準として残し、高速化した処理は同じ局面で合法手集合・遷移後の状態を比較する。最初から複数言語でエンジン全体を二重実装することは避ける。

GPU向けのPyTorch構成は、訓練PCのOSとGPUに合わせて選ぶ。現在の作業用PCを、そのまま訓練PCと見なさない。[PyTorch公式導入手順](https://pytorch.org/get-started/locally/)

## 4. ゲームエンジンの設計

### 局面と一手を、特殊ルールまで表現する

局面は盤上の駒だけでなく、手番、駒の状態、ルールに必要な履歴、反復判定に必要な情報を保持する。同じ盤面でも履歴によって合法手や終局が異なる場合は、別の状態として扱う。

一手は出発点と到着点の組だけに限定しない。移動経路、射撃対象、行動の終了、成りの選択など、採用ルールで必要になる選択を含む構造にする。同じ到着点でも結果が異なる行動を区別できるようにする。

画面上では一手を段階的に選択できるが、エンジンは手が確定するまで手番を渡さない。途中で生じる捕獲・特殊効果・終局の判定時点は、ルール仕様に従う。

### エンジンが公開する操作

- `initial_state()`：初期局面を作る。
- `legal_actions(state)`：完全な一手として合法な行動を列挙する。
- `apply_action(state, action)`：行動を検証し、次の局面と発生した出来事を返す。
- `outcome(state)`：続行・勝敗・引き分け等の状態と理由を返す。
- `serialize(state)` / `deserialize(data)`：必要な履歴を含めて保存・復元する。

複製や一手の取り消しは、探索性能を測定して実装方式を決める。局面を識別する値には、合法手・勝敗に影響する履歴を反映し、盤面だけが同じ状態を探索で誤って同一視しない。

### エンジンの検証

- 各駒の通常動作に加え、盤端、遮蔽物、捕獲制限、特殊効果の重なりをテストする。
- 初期配置、成り、反復、勝敗条件に、人が仕様から確認した期待結果を用意する。
- 自動生成した合法手を適用し、盤外への移動、駒の重複、不正な状態が起きないことを確かめる。
- 保存・復元と棋譜再生で、盤面、手番、履歴、合法手、終局結果が一致することを確かめる。
- 浅い探索で到達する局面数を回帰検証に使う。初回の実装が出力した件数だけを、ルールの正しさの根拠にはしない。

## 5. 人が遊べる対局画面

初期版で、次の操作と表示を用意する。

- 19路盤の座標、手番、駒名、成り・特殊状態の表示。
- 駒を選ぶと、合法な移動先・射撃対象・移動経路を表示する。
- 複数段階の行動は途中選択を表示し、確定前に取り消せる。
- 駒の動き方と、選択した行動の結果を確認できる。
- ローカルでの人対人、人対AI、AI対AIの観戦。
- 棋譜の保存・読込・再生、対局の中断と再開。
- AIの思考時間の設定と停止。画面操作を止めずに探索する。

盤面の拡大と移動を可能にし、駒名や経路を読めるようにする。実画面で、通常の移動・射撃・複数段階の行動をそれぞれ選択し、エンジンが適用した行動と表示が一致することを確認する。

## 6. 自己対戦による強化学習

### 探索と学習を組み合わせる

AIは採点NNとαβ探索に統一する。相手の応手まで読み、探索の末端にある局面をNNで採点する。ルールで確定した勝敗は、探索が勝敗点として扱う。

NN全体に線形経路と非線形経路を持たせる。線形経路は従来の駒価値と前進点を再現する重みで初期化し、非線形経路は出力層をゼロにする。学習前の評価は従来評価と一致し、学習では両方の経路を更新する。

広将棋用の具体的な学習設計は、次の順で検証する。

1. **初期状態の検証**：全駒種と先後について、NNの初期出力と従来評価が一致すること、同じ深さで探索した最善手が一致することを確認する。
2. **局面の入力**：駒種、所有者、手番、特殊状態、必要な履歴を数値に変換する。履歴を省いて合法手や勝敗を区別できなくならないか確認する。
3. **局面の採点**：エンジンが列挙した合法手をαβ探索で読み、NNは局面を指定された側から見た点数に変換する。
4. **小規模な学習**：行動後の盤面を入力とするQ値をDouble DQNで更新し、両方の経路が学習できることを検証する。相手の応手の価値は符号を反転する。
5. **自己対戦の反復**：探索とランダムな合法手の選択で対局し、経験を保存する。経験を再利用してNNを更新し、その重みを以後の探索に使う。

合法手の列挙件数が大きすぎる場合は、行動を段階的に選ぶ方式を比較する。その場合も、一手の途中で相手の手番に変わらない設計とし、完全な合法手を表現できることを検証する。

### 1台のGPUで動かす訓練処理

CPUで自己対戦を進め、保存した経験をGPUでまとめて学習する。`train_dqn` は自己対戦とNNの更新を交互に行う。目標値の計算では、学習用NNで相手の最善手を選び、定期的に同期する目標値用NNでその手を評価する。

小さな採点NNから始め、学習バッチ数、探索の深さ、思考時間を調整する。大きなモデルへの拡張は、メモリ使用量と対局生成速度の測定後に行う。

経験には、行動後の局面、指した側から見た報酬、ルールによる終局の有無を保存する。終局時の勝ちは +1、負けは −1、終局前の報酬は0とする。先後で評価の符号を取り違えないテストを用意する。実験では使用したコードのハッシュと初期モデルも保存する。

計算時間や手数の上限で止めた対局は、ルール上の引き分けと区別する。DQNでは途中の経験も次の局面の予測値を使って学習するが、打ち切りを終局にせず、勝敗のラベルも付けない。合法手がなく勝敗も未定義の局面からは目標値を作らない。未完了ばかりになる場合は、検証済みの終盤局面から始める実験を追加し、開始局面の分布を記録する。終盤からの実験と、正式な初期配置からの性能評価は分ける。

勝敗と探索評価を混ぜる従来の `train_value` はDQNとは別の学習経路として残す。DQNの実行条件、保存と再開、比較手順は `docs/ai-training.md` に記載する。

### 保存と再開

- モデルの重み、最適化処理の状態、学習回数、乱数の状態、設定を保存する。
- 学習データの構成、ルールの版、実行コードの版、使用した機器を記録する。
- データは一時ファイルから確定ファイルへ切り替え、途中停止で壊れたデータを読み込まない。
- モデルごとに自己対戦数、学習した局面数、所要時間、保存容量を追跡する。
- 同一実験の再開と、条件を変えた新しい実験を区別する。GPUでの完全な数値一致は前提にせず、再現性の範囲を記録する。

## 7. 棋力の評価と計算量の判断

学習処理が動くことと、AIが強くなることは別々に判定する。学習時の損失が下がっただけでは、棋力向上と判断しない。

評価相手は、初期重みの同じNNと過去のモデルとする。対局用モデルの更新前に、候補モデルを同じ探索と対戦条件で評価する。

- 先後を入れ替え、独立した複数の対局条件で比較する。
- 原則として1手あたりの実時間を揃える。探索回数を揃える実験は別に記録する。
- 勝ち・負け・引き分け・未完了の件数を分けて示す。完了対局の得点率は `(勝ち数 + 0.5 × 引き分け数) / 完了対局数` とする。
- 同じ初期局面と決定的なAIの反復を、独立した多数の対局として数えない。
- 対局ペア単位の再標本化などで得点率の信頼区間を算出する。候補モデルの採用例は「旧モデルに対する得点率の95%信頼区間の下限が50%を超え、特殊ルールの局面テストに回帰がない」とする。
- 評価対局の件数と判定時点を開始前に決める。結果が有利になるまで対局数を増やす判定はしない。
- 訓練に使わない局面問題も用意し、勝敗条件や特殊な捕獲を理解しているか別に調べる。

必要な対局数は、計測した対局時間と検出したい改善幅から決める。証拠が不足する場合は「改善未確認」として、旧モデルを対局用に維持する。

訓練PCでは、初期・中盤・終盤・特殊効果が集中した局面を測定対象にする。合法手数、合法手生成時間、探索速度、推論速度、1対局の所要時間、GPUメモリ、打ち切り率を測る。

訓練日数は実測した合計生成速度から見積もる。例えば、1日あたりの完了対局数は `全ワーカー合計の完了対局数/秒 × 1日に対局生成へ割り当てる秒数` となる。学習・評価に使う時間は別途確保する。広将棋で十分な棋力に達するまでの必要対局数は未確認であり、既存の将棋AIの訓練時間を流用しない。

## 8. 開発工程と工数

1名が週30時間を確保し、各工程を順に実施する場合の初期見積もりを以下に示す。数値は作業分解に基づく見積もりで、実績値ではない。目標棋力に到達するまでの追加学習期間は含めない。

| 工程 | 主な作業 | 完了条件 | 工数の目安 |
| --- | --- | --- | --- |
| P0：ルール仕様 | ルール記事の本文・図の確認と対局棋譜との照合、駒一覧、初期配置、特殊ルール、期待結果の作成、GPU環境の確認 | 初期版の全ルールを特定でき、実装を妨げる未決定事項が解消している | 1〜2人週 |
| P1：ゲームエンジン | 局面、一手、合法手、特殊効果、成り、終局、保存・復元、検証 | 採用ルールの全項目にテストがあり、対局と棋譜再生が一致する | 3〜5人週 |
| P2：対局画面 | 盤面、操作支援、ローカル対戦、棋譜再生 | 人対人とAIとの対局を画面で完了できる | 1〜2人週 |
| P3：探索AI | 採点NN、αβ探索、行動の表現、性能測定、必要な部分の高速化 | 制限時間内に合法手を返し、特殊ルールの局面で探索を検証できる | 2〜3人週 |
| P4：自己対戦と学習 | モデル、推論の一括処理、対局生成、学習、記録、途中再開 | 自己対戦からモデル更新まで完了し、停止後も継続できる | 2〜3人週 |
| P5：評価と統合 | 旧モデルとの対戦、評価レポート、人対AIへの接続、継続実行の確認 | 棋力の変化を判定でき、学習モデルで遊べる。改善未確認の場合も結果を報告できる | 2〜4人週 |

合計は **11〜19人週**。週30時間の場合、`11〜19 × 30 = 330〜570時間`。1名が順に進める場合は約3〜5か月が目安となる。学習に必要な実機時間が長い場合や、ルールの解釈・エンジンの高速化が難しい場合は、この範囲を超える。

- **P2完了時点**：人が遊べる広将棋。P0〜P2の合計は5〜9人週。
- **P4完了時点**：自己対戦でモデルを更新できる訓練基盤。P0〜P4の合計は9〜15人週。
- **P5完了時点**：学習したAIで遊べて、棋力の変化を評価できるソフト。棋力向上自体は実験で確認する。

P0完了時にルールの難しさを反映して工数を更新し、P3完了時に実測した計算速度から訓練計画を更新する。各工程は期間の経過ではなく、完了条件を満たして次へ進む。

## 9. 最初に着手する作業

1. ルール記事の本文と図を確認し、必要に応じて同じルールで行われた公開対局の棋譜と照合する。
2. 駒と初期配置の一覧、特殊ルールと解釈の相違点をまとめる。
3. 通常移動・射撃・複数段階の行動・連動する成り・終局について、入力局面と期待結果を作る。
4. 実際に訓練するPCのGPU、GPUメモリ、OS、CPU、メモリ、保存領域を確認する。
5. ルールと機器の確認結果から、一手の表現、技術構成、最初の実装範囲を決定する。

最初の実装成果物は、初期盤面の表示と代表的な行動の検証とする。この小さな実装で一手と局面の設計を確かめてから、全駒・全特殊ルールへ広げる。
